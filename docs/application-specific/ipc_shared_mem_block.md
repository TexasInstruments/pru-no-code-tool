## IPC Shared Memory Block

### Purpose

The IPC Shared Memory block manages inter-processor communication between the PRU and R5F/A53 host processors. It allocates static memory variables in the PRU's shared memory segments, acting as a gateway for sharing telemetry (e.g. current positions) or receiving commands (e.g. setpoints).

### Features

- Maps data variables to physical memory segments (`PRU_SHARED_RAM`, `PRU_DRAM_0`, `PRU_DRAM_1`)
- Emits structured variables with constant table addressing (e.g., `c28` pointer base)
- Auto-allocates memory offsets to avoid overlap and collisions
- Supports standard data types (uint32_t, int32_t, float, etc.)

### Configuration

| Parameter | Description | Default | Options |
|-----------|-------------|---------|---------|
| Variable Name | The reference label for host mapping | `pru_telemetry` | Text string |
| Memory Section | Physical RAM segment to allocate within | `PRU_SHARED_RAM` | `PRU_SHARED_RAM`, `PRU_DRAM_0`, `PRU_DRAM_1` |
| Data Type | Data width and representation | `uint32_t` | `uint8_t`, `uint16_t`, `uint32_t`, `float` |

### How It Works

The block maps the connected input data port to the allocated address in shared memory:
1. Resolves the memory section pointer (e.g. `c28` constant table for DRAM).
2. Calculates the local variable offset.
3. Emits `SBCO` instructions to store the input register value directly into the designated memory space:
   ```assembly
   SBCO    source_reg, c28, var_offset, size
   ```

### Important Notes

- `c28` is not a fixed address: it is `00nn_nn00h` with `nnnn` = `CTPPR0.C28_POINTER`, and `CTPPR0` resets to 0, which would make `c28` the core's own data RAM at `0x00000000`. For a block that uses `c28` (a `shared` mailbox), the generated code programs `CTPPR0 = 0x0100` at `sysconfig_generated_start` and after every group `_start:` label, so `c28` = `0x00010000` PRU shared RAM on silicon and in a pru-simulator that models `PRU_CTRL`. `c24` (`dmem0`) is the block index pointer and is correct at its reset value, so `dmem0` mailboxes need no write.
- The `CTPPR0` write is triggered by the text `c28` appearing in any instantiated block's macro, so `dmem0`-mode mailboxes and industrial gateways (whose macro mentions `c28` only inside an unused `.if` branch) also get the write. It is harmless but not needed there.
- The write costs about 4 cycles (`ldi`, `ldi32`, `sbbo`) once at `sysconfig_generated_start` and on every group `CALL`. The generated `OVERALL PEAK CYCLES` header includes it in a design that uses `c28`; the per-block cycle counts do not.
- The `CTPPR0` offset `0x28` and reset value 0 are documented for PRU_ICSSG (SPRUIM2J). For AM261x (PRU_ICSSM) they are inferred from the shared PRU-ICSS IP; SPRUJB6 does not describe the register.
- Always match the memory layout configured in host C files with the variable names and offsets generated by this block.

### Example Usage

1. Configure an IPC Shared Memory block with variable name `motor_pos` and data type `uint32_t`.
2. Connect the output of a BiSS-C absolute encoder block to the input of this block.
3. Generate code. The host processor (R5F) will read the current position at the shared memory offset allocated to `motor_pos`.
